# Port an OpenMRS form

## Target

- The target implementation is AMRS: `https://kibana.ampath.or.ke/openmrs`. Check it read-only.
- Ported forms run on the Angular form engine (openmrs-ngx-formentry), not the React form engine. Expression helpers and semantic checks follow the Angular engine.
- The primary preview is the target implementation's own Form Builder test instance, which renders with the Angular form engine — the forms team needs no repo or developer setup. The local ngx-formentry demo app (see [schema-validation.md](references/schema-validation.md)) is an optional developer-side smoke test. The upstream O3 Form Builder renders with the React engine; treat it as secondary and record engine-difference caveats.
- AMRS requires credentials for concept reads, OCL's anonymous API is disabled, and dev3 carries only a demo subset of CIEL. Live target metadata therefore comes from `scripts/fetch-target-metadata.mjs`, which the user runs with their own read-only credentials.

## Goal

Produce a review workbook and validated O3 JSON. Stop after the no-save preview. Do not save, publish, deploy, submit an encounter, or use patient data.

## Modes

- `review` (default): prepare real recommendations and team decisions.
- `exercise`: allow clearly labelled sample decisions or UUIDs.
- `release-candidate`: require verified active target metadata and no samples.

## Core rules

- Keep team-facing language simple.
- Check the target read-only. Never store credentials.
- Preserve the source. Record corrections separately.
- Match concepts by meaning, datatype, class, answers, mappings, and active state, not UUID equality.
- Never infer retirement; verify the actual target metadata.
- Use unique lower-camel-case field IDs.
- Set `published` to `false`.
- Block release-candidate status for pending decisions, samples, unverified metadata, or failed checks.

## Progress pattern

After each step, give only:

```text
Step N: STATUS
Result: ...
Next: OWNER — ACTION
```

Continue safe, read-only work immediately. Pause only for a real team decision, missing authority, or an unsafe assumption. Do not stop merely to ask “what next?”

Record every gate result in the workbook as it happens:

```text
python3 scripts/record-gate.py --workbook REVIEW.xlsx --step N --status Passed --evidence "..." [--action "..."] [--artifact "..."]
```

The workbook is the source of truth for run status. When resuming or reporting status, read it first — do not answer from memory.

## Steps 1–7

### 1. Capture source

Extract every question, answer, rule, group, section, and source identifier. Preserve original wording. Assign proposed field IDs.

For JSON sources, run:

```text
node scripts/extract-inventory.mjs SOURCE.json --report inventory.json
```

The review workbook is generated by `scripts/build-workbook.py` (after step 2) — plain sheets, no template, no styling, no formulas, no row limit. For non-JSON sources, hand-build `inventory.json` in the same shape extract-inventory.mjs produces, then generate the workbook the same way. Verify all sheets after generating.

Gate: source inventory is complete.  
Next: Claude checks target concepts.

### 2. Crosswalk

Read [concept-matching.md](references/concept-matching.md). Check the live target and relevant local content repository. Record evidence and classify each item.

For JSON sources, cross-reference the local content repository first:

```text
node scripts/crosswalk-local.mjs SOURCE.json --content-repo PATH --report crosswalk-local.json
```

When a dictionary snapshot exists (see [concept-matching.md](references/concept-matching.md)), derive target metadata from it first — no credentials needed:

```text
node scripts/snapshot-metadata.mjs SOURCE.json --report metadata-report.json   # uses the snapshot bundled in assets/; --snapshot DIR overrides
```

Snapshot evidence is dated and excludes retired concepts; it is enough for review mode. For release-candidate verification, ask the user to run `scripts/fetch-target-metadata.mjs` with their read-only credentials (see [schema-validation.md](references/schema-validation.md)).

Once the crosswalk exists, generate the filled workbook:

```text
python3 scripts/build-workbook.py --inventory inventory.json --crosswalk crosswalk-local.json --out FORM-review.xlsx --open
```

Add `--metadata-report metadata-report.json` when live evidence is available. `--open` shows the workbook in the user's spreadsheet app as soon as it is written; use it whenever a person is present. The script needs `openpyxl`; install it in an isolated virtual environment if missing, as for `jsonschema`.

Gate: every source item has evidence and a recommendation.  
Next: the forms and concepts team reviews exceptions.

### 3. Decide

Record `Approve target concept`, `Create new concept`, `Redesign question`, `Remove from target form`, or `Needs team decision`.

Do not invent clinical approval. In exercise mode, make decisions only when the user asks and label them as exercise decisions.

Gate: no unexplained pending rows remain.  
Next: Claude finalizes form design.

### 4. Design

Record pages, sections, order, labels, field IDs, type, rendering, required behavior, conditions, validation messages, and encounter metadata. Verify the encounter type live.

Gate: design is approved; release-candidate encounter metadata exists and is active.  
Next: Claude generates JSON.

### 5. Generate

Read [schema-validation.md](references/schema-validation.md). Generate JSON only from recorded decisions. Mark exercise files clearly.

Apply the workbook's recorded decisions:

```text
python3 scripts/apply-decisions.py --workbook REVIEW.xlsx --candidate FORM.json --out FINAL.json
```

It remaps approved concept UUIDs (including inside expressions), removes questions and answers marked `Remove from target form`, and sets the encounter type and form UUIDs from the Build Results header block. It reports how many concept rows still lack a team decision. Redesigns and new questions remain manual edits; record them in the workbook notes.

Gate: workbook and JSON agree; JSON remains unpublished.  
Next: Claude validates it.

### 6. Validate

Run:

```text
# Live target metadata (the user runs this; required for release-candidate)
node scripts/fetch-target-metadata.mjs FORM.json --base-url TARGET_URL --report metadata-report.json

node scripts/audit-o3-form.mjs FORM.json --mode MODE --metadata-report metadata-report.json --report semantic-validation.json

# Windows
py -3 scripts/validate-canonical-schema.py FORM.json form.schema.json --report canonical-validation.json

# macOS/Linux
python3 scripts/validate-canonical-schema.py FORM.json form.schema.json --report canonical-validation.json
```

Choose the launcher automatically. On Windows, use `python` if `py -3` is unavailable. On macOS/Linux, use `python` if `python3` is unavailable.

Use the current canonical schema from:

`https://raw.githubusercontent.com/openmrs/openmrs-contrib-json-schemas/main/form.schema.json`

Use Python with `jsonschema`. If it is missing, create an isolated virtual environment and install `jsonschema` after any required approval; do not change global Python. If installation fails, report the blocker and one clear next action. Never claim validation passed.

After the first validation run, do the mechanical pass — corrections that need no clinical judgment — then validate again:

- Normalize malformed field IDs to readable lower camel case, propagate every rename through every expression, and re-verify the affected conditions in a preview.
- Chase each remaining warning to a named recommendation in the workbook (dead validators copied from other forms, engine-unsupported features, meaning mismatches).
- Draft the new-concepts Initializer CSV for missing concepts: keep custom v4 UUIDs, mint fresh UUIDs for CIEL-style ones unless the CIEL meaning is verified, check every proposed fully specified name against the dictionary snapshot (an exact name match becomes a map-to-existing suggestion for the team, not a create row), and verify every answer UUID is either created in the CSV or active on the target.

Gate: canonical, semantic, reference, and required metadata checks pass.  
Next: Claude runs the no-save preview.

### 7. Preview

Before handoff, adversarially review the form's logic against the Angular engine source (openmrs-ngx-formentry): every expression identifier, alert shape, rendering type, and coded-value comparison should be checked against what the engine actually executes — this catches render-blocking defects without any preview environment.

Then hand the validated candidate to the forms team to preview in their own instance's Form Builder (Angular engine, no setup needed), using the checklist in [schema-validation.md](references/schema-validation.md): rendering, conditions, exclusivity, repeat groups, required behavior, and validation messages, without saving. When a developer environment is available, the ngx-formentry demo app (same reference) is an optional local smoke test; revert the demo repo afterwards.

Gate: preview checks pass or remaining submission-only checks are explicit.  
Next: the team replaces blockers or hands the validated candidate to the separate release workflow.

## Outputs

- Completed review workbook
- O3 JSON
- Semantic and canonical validation reports
- Preview results
- Short handoff with status and next action
- A plain-language "What the team does next" list: the row-by-row decisions to make, each named call (encounter type, remaps, redesigns) with counts, the header-block cells to fill, and where they test the result. Assume the reader has no developer tools.

Use one status:

- `READY FOR TEAM REVIEW`
- `VALIDATED EXERCISE - NOT FOR DEPLOYMENT`
- `VALIDATED RELEASE CANDIDATE`
- `BLOCKED`

## Resume

Inspect existing artifacts, find the last gate supported by evidence, preserve decisions, and continue. Recheck stale target metadata. After any concept, ID, structure, or rule change, rerun every downstream check.
